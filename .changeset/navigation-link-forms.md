Navigation link forms (#248, stage 1 — the widget prerequisites for the navigation rule: a control that navigates to another page is a link with an href; anything else is a button element with a callback). `Button` gains an href form: pass `href` instead of `onPress` and the same frame, variants, and sizes render as a real anchor carrying the href on web (on native, a press opens the href through the platform link path — the href is forwarded verbatim to `Linking.openURL`, so native hosts pass a scheme-bearing absolute URL such as the app's deep link or an https URL, while root-relative paths are web destinations; the host composes the per-platform href); a disabled href Button renders dimmed, announces its disabled state, and is not followable. `TextLink` gains the same href form for in-prose navigation, and `BackLink` gains an optional `href` for hosts with a canonical back destination — the drawn-arrow row renders unchanged inside the anchor. `Tabs` gains a link variant (`variant="link"`, items carry `href`): each tab is a real anchor and the current page's tab is marked, while the default button variant still switches in-page content. On a @spudly/ui bump, re-check in Storybook: Components/Button's Link, LinkVariants, and LinkSizes stories render anchors (the DOM node is an `<a>` with the href; right-click offers "Open in new tab") visually identical to the button stories, and LinkDisabled is dimmed and not followable; Components/TextLink's Href and HrefInProse stories carry their hrefs; Components/BackLink's Href story links back to its destination with the arrow centered on the label; Components/Tabs' LinkNavigation story shows four anchor tabs with Search marked current, while RecipeDetail (button variant) still switches tabs in place.
