Recipe form sortable lists land as design-system views (#130, tranche T4): RecipeIngredientListView / RecipeInstructionListView (the list chrome: labeled section, add action, empty state) compose RecipeIngredientRowView / RecipeInstructionRowView (the settled #124 row contracts — {key, quantity, unit, name} ingredient rows, {key, body} instruction rows), emitting field-change, add, and remove intents keyed by row. RecipeFormPage gains `ingredients` and `instructions` data props that render these views; the existing `renderIngredientsSection` / `renderInstructionsSection` slots remain as fallbacks for unmigrated hosts, and a data prop wins when both are passed. Per Stephen's 2026-11-09 drag boundary, no drag library enters the design system: hosts keep their drag containers (dnd-kit on web, DraggableFlatList on native) and bind the handle through the views' `renderDragHandle` / the rows' `dragHandle`, with reorders crossing back as new rows arrays. Test: open the RecipeFormPage stories (or the Views/RecipeIngredientListView and Views/RecipeInstructionListView stories), edit row fields, add and remove rows, and confirm each intent updates only the intended row and empty lists show their empty lines.
