Add `VerseSearchPage` and `MyVersesPage` to the `@spudly/ui/pages` subpath (spudly/design-system#49): Memorize's two list screens — the Search tab and the "My verses" home tab — as controlled page components, following the RecipesPage pilot. The app keeps all state and business logic (the query text, the search against its scripture data source, the memorize store and its mutations, drill navigation) and drives both views entirely through props. VerseSearchPage mirrors the real SearchScreen — the "Search verses" heading, the demo-set info notice when the app has no API key, the search row (the DS SearchField plus a Search button disabled while searching or on a blank query; both submit-editing and the button fire the one `onSearch`), the app's error message as an error alert, a busy spinner above a results list that stays mounted across re-searches, and result cards (reference, verse text, "Add to memorize list" → `onAddVerse(id)`). It deliberately has no empty state: the app renders an empty list before the first search and after a fruitless one. MyVersesPage mirrors VersesScreen — the "My verses" heading, the app's empty state verbatim when the list is empty, and rows carrying reference, a status badge (the status as its text; memorized → success tone, learning → info), verse text, an optional pre-composed next-review line, and Drill / Remove callbacks by id. Neither component takes a render slot: the audit found no app-rendered content inside either screen, so every action is a pure intent callback. Stories render the real components in the Quiet Dawn theme (VerseSearchPage: Default, DemoMode, Searching, Error, NoResults; MyVersesPage: Default, Empty), and source-scan contract tests pin the shells, callback wiring, state behavior, and the deliberate no-slot / no-empty-state decisions.
